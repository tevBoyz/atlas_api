# Atlas API

NestJS (Fastify) backend for the Atlas mobile app. It runs on the existing Atlas PostgreSQL 17.11
database (hosted on Supabase) and replaces the Supabase SQL functions area by area.

## Quick start (local, fake data)

Needs Node 24 (`.nvmrc`) and Docker Desktop. From a fresh clone:

```sh
npm ci
docker compose up -d --wait   # Postgres 17.11 (Supabase image) on 127.0.0.1:54329, Redis 7 on 127.0.0.1:63799
npm run db:setup              # baseline (37 migrations) + API migrations + fake seed data
npm run start:dev             # API on http://localhost:3000 (GET /healthz, GET /readyz)
```

`db:*` scripts use the local docker database automatically when `DATABASE_URL` is not set. To
point the API itself at it, copy `.env.example` to `.env` and set the local values shown there
(`DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres`,
`REDIS_URL=redis://127.0.0.1:63799`).

## Database scripts

| Script                         | What it does                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------- |
| `npm run db:setup`             | `db:baseline`, then `db:migrate`, then `db:seed`.                                                 |
| `npm run db:baseline`          | Verifies checksums, then applies `db/baseline/*.sql` in file-name order to an **empty** database. |
| `npm run db:baseline:verify`   | Checksums only (no database).                                                                     |
| `npm run db:baseline:manifest` | Rewrites `db/baseline/checksums.sha256`. Only for a deliberate, reviewed baseline refresh.        |
| `npm run db:test:sql`          | Runs the 7 behavioural SQL tests in `db/baseline/tests/` against the local database.              |
| `npm run db:migrate`           | Applies API-owned SQL migrations from `db/migrations/` (tracked in `api_schema_migrations`).      |
| `npm run db:seed`              | Inserts fake users, complete profiles and one Safety Circle. Idempotent.                          |
| `npm run db:introspect`        | Regenerates `src/db/schema.ts` (Drizzle) from the local baselined database.                       |

### Production safety

- Every script that connects refuses any host other than `localhost`, `127.0.0.1` or `::1`, and
  refuses URLs whose query parameters (`host`, `hostaddr`, `port`, `service`) could redirect the
  connection. Output names the target as `host:port/database` only, never credentials.
- `DATABASE_URL` is resolved like the API does: a real environment variable wins over `.env`; if
  neither sets it, the local docker database is used. If your `.env` points at a hosted database,
  the scripts refuse; override it for one command instead:
  - Git Bash: `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres npm run db:seed`
  - PowerShell: `$env:DATABASE_URL='postgresql://postgres:postgres@127.0.0.1:54329/postgres'; npm run db:seed`
- `--allow-remote` (e.g. `npm run db:migrate -- --allow-remote`) lifts the rule. It exists only for
  an approved deploy step on Dawit's instruction. Never use it for tests or experiments.

### Baseline (`db/baseline/`)

The 37 Supabase migrations and 7 SQL test files are stored **unchanged** (epic §18 D1).
`db/baseline/checksums.sha256` lists a SHA-256 per file (line endings normalized, so a Windows
CRLF checkout matches). An edited, missing or unlisted file stops `db:baseline` before anything
runs. The whole baseline runs in one transaction, as the `postgres` role (as on Supabase).

Re-running is safe: when the same baseline is already applied it does nothing; any other non-empty
database is refused. The applied baseline is recorded in the local-only schema `atlas_local`.
To start over: `docker compose down -v` then `docker compose up -d --wait`.

**Local shim.** The `supabase/postgres` image has the Supabase roles, the `supabase_realtime`
publication and the initial `auth` schema, but on a real project the Auth (GoTrue) and Storage
services add the rest at startup. `db/local/supabase-services-shim.sql` adds the subset the baseline
needs (`auth.users` phone/confirmation columns, current `auth.uid()`/`auth.jwt()`, `storage.buckets`,
`storage.objects`, `storage.foldername()`). Docker runs it once, when the volume is created. It is
never applied to a hosted database.

### API migrations (`db/migrations/`)

Plain SQL, named `<number>_<snake_case>.sql`, applied in number order, each in its own transaction,
recorded in `public.api_schema_migrations (id text primary key, applied_at timestamptz)`.
**Additive and backward compatible only** while the app and the SQL functions share the database.
See `db/migrations/README.md`.

### Drizzle schema (`src/db/schema.ts`)

Generated by `npm run db:introspect` (drizzle-kit pull + a deterministic post-processing step) for
`profiles`, `safety_circles`, `safety_circle_members`, `incidents`, `incident_deliveries`,
`incident_events`, `app_config`, `login_lockouts`, the API-owned `idempotency_keys`, plus a read-only `authUsers` subset of
`auth.users` (`id`, `email`, `phone`, `email_confirmed_at`, `phone_confirmed_at`, `created_at`).
Do not edit it by hand, and never use drizzle-kit generate/push: schema changes are SQL migrations.
Never write `activated_at` on `safety_circle_members`; the trigger owns it.

### Seed data

Fake only: Ada (circle owner), Ben and Cara (active members), Dan (pending phone invite). Emails
`*@example.test`, phones `+1 201 555-0101` to `-0104` (fictional range), fixed ids
`00000000-0000-4000-8000-…`. Never put real people's data in the seed.

## Database role (epic §18 D10)

- **Production:** the API uses the **existing database role** of the Supabase project (no dedicated
  least-privilege role for now). The connection string lives only in the server's environment /
  secret store (`DATABASE_URL`), never in the app or this repo.
- **What the API needs** (and any future dedicated role must have):
  - `USAGE` on schema `auth` and `SELECT` on `auth.users` (read-only).
  - `USAGE` on schema `public`; `SELECT, INSERT, UPDATE, DELETE` on the app tables (`profiles`,
    `safety_circles`, `safety_circle_members`, `incidents`, `incident_deliveries`,
    `incident_events`, `app_config`, `login_lockouts`, `login_lockout_rpc_throttle`) and on
    API-owned tables; `EXECUTE` on the public functions it calls during the transition.
  - Must not be `anon` or `authenticated` (the `activated_at` trigger and RLS treat those as
    clients). RLS: the API enforces authorization in code, so its role reads tables with RLS
    bypassed (`postgres` has `BYPASSRLS` on Supabase) or must be granted equivalent access.
  - **No superuser at runtime.** Migrations (`db:migrate`) need `CREATE` on schema `public`; they
    run as a deploy step, not from the running API.
- **Locally:** the API and scripts connect as `postgres` (password `postgres`, local only). As on
  Supabase it is not a superuser but has `BYPASSRLS`, owns the baseline objects and can read
  `auth.users`, which matches production.

## Health and readiness (API-100-07, `src/health`)

| Route          | Answers                                                                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /healthz` | Always `200 {"status":"ok"}` while the process runs. No dependency checks.                                                               |
| `GET /readyz`  | `200 {"status":"ok"}` when a DB query, a Redis `PING` and the migrations check pass; else `503 {"status":"unavailable","failed":[...]}`. |

- Both are at the root (no `/v1`), send `cache-control: no-store`, and are marked `@Public()` and
  `@SkipRateLimit()` (`src/common/guards/route-access.ts`). **The JWT guard (API-100-08) and the
  rate limiter (API-100-11) must skip routes carrying that metadata** (`isPublicRoute`,
  `skipsRateLimit`).
- `failed` lists only the failing checks, always in the order `db`, `redis`, `migrations`.
- **Exemption from the error envelope**: the 503 body is exactly `{"status","failed"}`, not
  `{"error":{...}}`. The controller sets the status and returns the body; nothing is thrown, so the
  global filter never sees it. Every other non-2xx response still uses the envelope.
- Each check has a 1.5 s timeout and they run in parallel, so `/readyz` answers within ~1.5 s even
  when a dependency hangs.
- **Migrations check**: every API migration in `db/migrations/` must be recorded in
  `public.api_schema_migrations`. With no migration files it passes without querying (the table
  may not exist). The built app reads the list from `dist/migrations-manifest.json`, written by
  `npm run build` (the Docker image copies `db/migrations/` into the build stage for this only);
  running from source (tests) reads `db/migrations/` directly. When DB is down and migrations
  exist, both `db` and `migrations` are reported.
- **Logging**: their `request completed` line is written at **debug** (any status), so load
  balancer polling does not flood the logs at `LOG_LEVEL=info`. Readiness logs only **changes**:
  `readiness: unavailable` (warn, with `failed` and per-check `reasons`) and `readiness: ready`
  (info). Redis logs `redis unavailable, reconnecting in the background` (warn) once per outage
  and `redis connection restored` (info).

### Data stores (`src/db/database.service.ts`, `src/redis/redis.service.ts`)

- `DatabaseService`: node-postgres `Pool` (max `DATABASE_POOL_MAX`, 5 s connect timeout) with
  Drizzle (`.db`, schema `src/db/schema.ts`) and `.query(sql, params)`. Opens connections only when
  used.
- `RedisService`: one ioredis client (`.client`). Connects after startup without blocking it,
  reconnects in the background, offline queue off (commands fail at once while disconnected).
  BullMQ (jobs story) uses its own connections.
- Fail-soft: the API boots and `/healthz` answers while Postgres or Redis is down; `/readyz` reports
  it. With `DATABASE_URL` / `REDIS_URL` unset (development/test only) `/readyz` reports `db` /
  `redis` as failed. Both are closed on shutdown (`enableShutdownHooks`).
- **Production safety**: outside `NODE_ENV=production` the API refuses to start when
  `DATABASE_URL` or `REDIS_URL` names a host other than `localhost`, `127.0.0.1` or `::1` (or a
  database URL with `host`/`hostaddr`/`port`/`service` parameters). The error names the key and the
  host only. `ALLOW_REMOTE_DATA_STORES=true` lifts the rule, only on Dawit's instruction.
- Unit tests (`npm test`) never connect: `src/testing/unit-env.ts` removes the URLs. The other suites
  start their own containers (see Tests).

## Errors (API-100-05, `src/common/errors`)

Every non-2xx response has one body shape (spec §11.2):

```json
{
  "error": {
    "code": "submit_emergency_alert:invalid_type",
    "message": "Choose a valid emergency type.",
    "details": {}
  }
}
```

- **Parity codes** (`fn:code`, spec §7) are typed constants in `error-codes.ts`. Raise them with
  `throw new DomainError('mark_incident_safe:not_open')`; the HTTP status comes from the central
  §11.2 table in `http-status.ts`. Messages are fixed English strings (never built from input).
  `rate_limited` takes `{ retryAfterSeconds }` (sets `Retry-After`); `login_lockout:locked` takes
  `{ details: LockoutStatus }`.
- **`@Operation('fn')`** on a route names the SQL function it replaces. A raw database
  `raise exception 'circle_full'` (the capacity trigger) then becomes `<fn>:circle_full`; a raised
  `fn:code` from an SQL function maps as-is. Any other database error is a 500.
- **Validation**: `@ZodBody(schema, codes?)`, `@ZodQuery(...)`, `@ZodParam('id', schema, codes?)`.
  The first failing field gives 422 with the operation's parity code when declared
  (`{ fields: { location_source: 'attach_incident_location:invalid_source' } }`, or `fallback` for
  any failure), else `validation:invalid_request`; `details.field` names the field (dotted path).
  Declare schema fields in the SQL function's check order (first failing check wins).
- **Generic codes** (API-only): `validation:invalid_request` 422, `internal:error` 500, and
  framework errors `http:not_found` 404 (unknown route; Fastify answers 404, not 405, for a wrong
  method), `http:bad_request` 400 (unreadable/empty JSON), `http:payload_too_large` 413,
  `http:unsupported_media_type` 415, `http:unauthorized` 401, `http:forbidden` 403, and the other
  `http:*` codes in `error-codes.ts` (any other 4xx keeps its status as `http:client_error`).
- **Unexpected errors** (and any deliberate 5xx `HttpException`) → 500 `internal:error`: no
  message, stack or SQL in the body; logged at `error` with the request id and reported to Sentry.

## Authentication (API-100-08, `src/common/auth`, `src/common/guards`)

- **Every route needs `Authorization: Bearer <access token>`** unless it is `@Public()` (today
  `/healthz` and `/readyz`; `GET /v1/invites/{token}/status` when it is built). Until own auth
  (Phase 6) the token is the app's **Supabase access token**.
- **Verification** (`SupabaseTokenVerifier`, behind the `TokenVerifier` interface for own tokens
  later): ES256/RS256 via `SUPABASE_JWT_JWKS_URL` (cached 10 min; an unknown `kid` refetches, at most
  once per 30 s) and/or HS256 via `SUPABASE_JWT_SECRET`. Checks `exp` (required) and `nbf` with
  `SUPABASE_JWT_CLOCK_SKEW_SECONDS` (0-30, default 30), `aud` = `SUPABASE_JWT_AUDIENCE`,
  `iss` = `SUPABASE_JWT_ISSUER` (required: no issuer = every token refused), `role = authenticated`,
  not anonymous (`role anon` or `is_anonymous: true`), `sub` a uuid. No table is read.
- **401** for a missing, malformed, invalid or expired token, with the route's parity code
  `<fn>:not_authenticated` from its `@Operation('<fn>')`. A JWKS that cannot be reached is a 500
  (never a 401, so an outage does not sign users out).
- **Route contract** (checked at boot, `route-contract.ts`): every non-public route declares
  `@Operation('<fn>')` with a `<fn>:not_authenticated` catalogue code, and `@Idempotent()` routes
  are not public. A violation stops the app from starting.
- Handlers get the caller with `@CurrentUser() user: AuthenticatedUser` (`id` = `sub`).
- **Local test tokens**: set `SUPABASE_JWT_SECRET` in `.env` to a random local value (32+
  characters, never the real project's secret), restart the API, then
  `npm run auth:test-token -- [--sub <uuid>] [--minutes 60] [--expired] [--role anon]` prints a
  token only this API accepts. Automated tests sign with local keys only (`src/testing`).

## Authorization policies (API-100-09, `src/common/policies`)

The RLS rules of spec §11.4 as code, one predicate per policy: `profile.self`, `circle.owner`,
`circle.activeMember`, `circle.activeMemberSince` (rule 54 window: `activated_at <= t`, false on any
null), `incident.resident`, `incident.memberView`, `incident.eventsView`, `incident.countsView`,
`delivery.own`, `invite.recipient`, `membership.activate`.

- List form: `policy.where({ callerId })` is a Drizzle `SQL` boolean over the table's columns
  (or a table alias: `incidentAlias('i')`).
- Single row: `policy.check(db, args)` / `policy.checkById(db, id, callerId)` evaluate the same
  predicate in one query (`db` may be a transaction).
- Hidden existence: `requireIncident(db, policy, id, callerId, '<fn>')` raises `<fn>:not_found`.
- Timestamps compare in Postgres at microsecond precision; pass database text, not a JS `Date`.

## Idempotency (API-100-10, `src/common/idempotency`)

- `@Idempotent('required' | 'optional')` on a route. Required: no `Idempotency-Key` → 400
  `idempotency:key_required`; not a UUID → 422 `idempotency:invalid_key`.
- Keys are per user, stored in `idempotency_keys` (migration `0001`) with a SHA-256 of method + URL +
  canonical JSON body. First use runs the handler; the response actually sent (2xx or 4xx, including
  error envelopes) is stored. A replay returns it with `Idempotent-Replayed: true` and does not run
  the handler. Different method/path/body → 422 `idempotency:key_mismatch`. Still running → 409
  `idempotency:in_progress` + `Retry-After: 1`; a claim older than 60 s is abandoned and runs again.
  5xx is not stored (retryable). Keys expire after 24 h (purged when presented, swept every 10 min).
- The table is closed to the `anon` / `authenticated` roles (no grants, RLS on).

## Rate limiting (API-100-11, `src/common/rate-limit`)

- **Limits** (requests per sliding window, configurable, see `.env.example`):

  | Policy            | Default    | Key             | Applies to                           |
  | ----------------- | ---------- | --------------- | ------------------------------------ |
  | `authenticated`   | 300 / 60 s | user            | every authenticated route by default |
  | `public`          | 60 / 300 s | IP              | every `@Public()` route by default   |
  | `emergency_write` | 30 / 60 s  | user            | `@RateLimit('emergency_write')`      |
  | `location_ping`   | 30 / 60 s  | user + incident | `@RateLimit('location_ping')`        |
  | `auth_failure`    | 120 / 60 s | IP              | requests rejected by authentication  |

- Over the limit: 429, `Retry-After` and `rate_limit:exceeded` (or the policy's own `code`).
  `@SkipRateLimit()` routes (health, readiness) are never limited or counted.
- **Atomic**: one Lua script does the whole check, including the expiry, with Redis `TIME`.
- **Fails open**: when Redis is down or slower than `RATE_LIMIT_REDIS_TIMEOUT_MS` the request goes
  through. An outage logs one warning and its end one info line.
- **Order** (`RequestGuard`): authentication, then the limit, then interceptors, so a 429 is never
  stored as an idempotent response. A rejected token counts against its IP; a valid token never does.
- **Client IP**: the first `x-forwarded-for` value when `TRUST_PROXY` is on, else the socket address.
  **A client can set that header itself**, so production must sit behind a proxy that overwrites it.

## Audit log (API-100-14, `src/modules/audit`)

- `AuditService.record(entry, tx)` writes `audit_log` (migration `0003`) inside the caller's
  transaction. Request id and IP come from the per-request context (`AsyncLocalStorage`).
- **Append-only**: triggers refuse UPDATE, DELETE and TRUNCATE for every role, including the role the
  API connects as, which owns the table (epic §18 D10). Closed to `anon` / `authenticated`.
- `detail` is sanitized (`audit.detail.ts`): medical and share fields, tokens, phone numbers,
  coordinates and free text are left out, and a warning names the keys. There is no read endpoint.

## Emergency submit (API-100-15, `src/modules/incidents`)

- `POST /v1/incidents` with `{"emergency_type": "..."}` and a required `Idempotency-Key`. **201**
  `created` or `promoted` (legacy `activating` row), **200** `renotified` when an alert is already
  open. The body is IncidentSend plus `submit_outcome`.
- One transaction with the locks of `submit_emergency_alert`, in its order: the profile row, then
  the open incident. SQL and API callers can run side by side on the same database.
- The audit row is written inside the transaction. Post-commit hooks
  (`INCIDENT_POST_COMMIT_HOOKS`, empty until API-100-41 and API-100-48) run only after the commit,
  are not awaited, and can never fail an alert that has committed.
- Audit `detail` holds `recipient_count` and `submit_outcome` only. Database errors are replaced
  before they are logged, so query parameters and row values never reach the logs.

## Open and recent incidents (API-100-16, `src/modules/incidents`)

- `GET /v1/me/incidents/open` → `{"open_incident": IncidentSend | null}` (always the wrapper). The
  incident is the same JSON submit returns, minus `submit_outcome`.
- `GET /v1/me/incidents?limit=n` → the caller's `active`/`resolved` incidents, newest
  `activated_at` first (then `id` desc). `limit` missing → 5; any integer is clamped to 1-20; a value
  that is not an integer (`abc`, `2.5`, empty, outside int4) → 422 `validation:invalid_request`
  with `details.field = "limit"`.
- Read-only transactions in UTC; only the caller's own incidents (`incident.resident`).

## Live location (API-100-17, `src/modules/locations`, `src/modules/config`)

- `GET /v1/config/live-location` → `{"interval_seconds", "stale_threshold_seconds"}` from
  `app_config`, read with the SQL function's own expression; not a JSON number or ≤ 0 → 12 / 45. A
  JSON number that is not an integer (`12.5`, `12.0`) makes Postgres raise, as
  `get_live_location_config()` does (the API answers 500).
- `POST /v1/incidents/{id}/locations` (`location_ping` rate limit, per user per incident) →
  IncidentShared. Body values go to Postgres as input text, as PostgREST passed them, so numeric
  strings, `NaN`/`Infinity` and any timestamp Postgres accepts (no offset = UTC) behave as through
  PostgREST. Order: `{id}` uuid input → body a JSON object → each value converts to its SQL type
  (422 `validation:invalid_request` + `details.field`) → `invalid_source` → `invalid_location` →
  row lock (`not_found`) → `not_open` → out-of-order guard (an older fix is 200 with the current row;
  compared in Postgres) → write. Never notifies; no audit row; coordinates are never logged.
- Post-commit hook `afterLocation` (realtime `incident.location`, API-100-41) after a stored ping.

## Live note and explicit re-notify (API-100-18, `src/modules/incidents`)

- `PUT /v1/incidents/{id}/notes` `{"incident_notes": string | null}` → IncidentShared. Own incident in
  `activating`/`active`; trimmed with `btrim` (spaces only) and counted with `char_length` (code
  points) in Postgres; empty → null; > 250 → 422 `too_long`; `incident_notes_updated_at` stamped on
  every write. A non-string note is 422 `validation:invalid_request`. Audit `incident.notes_set`
  (`{cleared}` only); hook `afterNotes`.
- `POST /v1/incidents/{id}/renotify` → IncidentSend. The same re-notify as a submit on an active alert
  (`IncidentsService.applyRenotify`); no Idempotency-Key (spec §11.3 E4). Audit `incident.renotified`;
  hook `afterRenotify`.
- `{id}` accepts what Postgres accepts as uuid input (any case, hyphens optional, braces); anything
  else is 422 on field `id`.

## Own circle, capacity and member list (API-100-24/25, `src/modules/circles`)

- `GET /v1/me/circle/capacity` → Capacity `{limit, active_count, pending_count, used, available}`,
  built by Postgres with the same `jsonb_build_object` as `_circle_invite_capacity_json` (same keys,
  order and integer types). Owner excluded; only active and **valid pending** rows use a slot.
  Caller without an owned circle → 403 `circle_invite_capacity:not_owner`. No location-sharing check.
- `GET /v1/me/circle` → `{circle, members, capacity}`: the `safety_circles` row (column order, as
  PostgREST's `select *`), the owner view of the member list and the capacity, from one
  `repeatable read` snapshot so members and capacity always agree. `{circle: null, members: [],
capacity: null}` when the caller owns no circle. Never `invite_token`. 401 code
  `safety_circles:not_authenticated`.
- `GET /v1/circles/{circle_id}/members` (`list_circle_members`): unknown circle → 404 `not_found`;
  neither owner (`circle.owner`) nor active member (`circle.activeMember`) → 403 `not_authorized`.
  Owner: every row, 14 keys, a pending row past its expiry as `expired`. Member: active rows only, 8
  keys. Names: an active row with a user shows that user's profile `full_name` (Postgres `trim`,
  spaces only), else the stored name. `avatar_url` = `{SUPABASE_URL}/storage/v1/object/public/{AVATARS_BUCKET}/{avatar_path}`
  (bare path when `SUPABASE_URL` is unset, as the SQL without a Host header; `http(s)://` paths kept).
  Ordering, including `lower(name)`, runs in Postgres (database collation, as the SQL).
- **Shared slot rules** (`invite-slots.ts`): `holdsSlot` (spec "valid pending"), `inviteLookupStatus`
  and the shown member status, each as a TypeScript function (microsecond-precise, `now` from the
  database) and a SQL form; both are tested against `_circle_invite_holds_slot` /
  `_circle_invite_lookup_status`. Every Phase 2 story uses them.
- Reads only; no row locks (the SQL functions take none) and no audit rows.

## Invitee side of an invitation (API-100-29/30, `src/modules/invites`)

- `GET /v1/invites/{token}/status` (`lookup_circle_invite`): **public**, limited per IP by the
  `public` policy (`RATE_LIMIT_PUBLIC_*`, default 60 / 5 min), `cache-control: no-store`. Body
  `{status, invite_expires_at}` only (lookup precedence of spec §5.3); blank or unknown token →
  `not_found`. Never a name, phone or id.
- `POST /v1/invites/{token}/preview` (`preview_circle_invite`): the status logic of spec §7.3
  (`own_circle`, `already_member`, `consumed`, `canceled`, `expired`, `circle_full`, `pending`,
  `not_found`) and its key rules; claims a pending invitation the caller may accept (`user_id`, still
  `pending`; a clash is 409 `duplicate_membership`). `claimed` is `null` where the SQL returns null
  (e.g. the owner previewing an unclaimed invitation). `owner_avatar_url` as the member list's.
- `POST /v1/invites/{token}/accept` (`accept_circle_invite`): locks the circle row, then the member
  row; checks and codes in the SQL order; the write stores the accepter's profile name (or keeps the
  stored one) and is the **only** member-row write that sets `active` (`membership.activate`,
  covered by `test/int/membership-activation-routes.int-spec.ts`). `activated_at` comes from its
  trigger. Same body without a write when already active for the caller.
- `POST /v1/invites/{token}/decline` (`decline_circle_invite`): member-row lock only; `declined`,
  with the caller as `user_id` unless that clashes; a second decline is `canceled`.
- Tokens are trimmed (spaces only, as Postgres `trim`); text Postgres cannot hold is 422 on `token`.
  Logs carry the route template only; traces and free text scrub `invites/<token>`.
- Audit `circle.invite.accepted` / `circle.invite.declined` in the same transaction (ids, channel,
  previous status; never a phone, name or token). No SMS, email or push.

## OpenAPI and the Dart client (API-100-12, `src/openapi`, `clients/dart`)

- Every route declares `@ApiContract({ operationId, summary, tag, responses, ... })` with zod schemas.
  Bearer security, the `Idempotency-Key` header, 401, 429 and the error envelope are derived from the
  route's own decorators.
- A schema wrapped in `componentSchema('Name', ...)` is published once and referenced by `$ref`
  wherever it is nested, so the Dart client gets one class. An array response needs no name: it is
  written inline and typed as a list of its (named) items.
- `npm run openapi:generate` writes `openapi.json`; `npm run openapi:check` fails on any byte
  difference. Neither needs a database, Redis or `.env`.
- `GET /v1/openapi.json` is public while `OPENAPI_ENABLED` is on (default) and always 404 in production.
- `npm run client:dart:generate` regenerates `clients/dart/lib/src/generated`;
  `npm run client:dart:build` analyzes and tests the package. Needs the Dart SDK, not Java. The package
  version is `API_VERSION` (`src/app.constants.ts`), which must match `package.json`.

## Tests

Needs Docker running. No suite uses the compose stack or reads `.env`.

| Script                  | What it runs                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------- |
| `npm test`              | Unit tests. No containers.                                                             |
| `npm run test:int`      | `test/int`: integration tests against real Postgres and Redis containers.              |
| `npm run test:baseline` | Each SQL file in `db/baseline/tests` must end with its `<name>_ok` exception.          |
| `npm run test:parity`   | `test/parity`: one named test per SQL assertion (`it.todo` until the endpoint exists). |

- One Postgres and one Redis container per run (`test/support/global-setup.ts`), on random ports, with
  the baseline and API migrations applied once into a template database.
- **Isolation**: each Jest worker has its own database and Redis index, and both are reset before every
  test file, so suites may commit real rows.
- Fixture builders are in `test/support/fixtures.ts`, the token factory in `src/testing/test-tokens.ts`.
- `test/parity/assertion-coverage.spec.ts` fails when a SQL assertion has no named parity test.

## Observability (API-100-06, `src/observability`)

- **Logs**: pino JSON on stdout, level from `LOG_LEVEL` (`silent` turns them off). Nest's own
  logs use the same logger. Every line of a request has `request_id`.
- **Request id**: the incoming `x-request-id` when it is 1-128 characters of `A-Z a-z 0-9 . _ : -`,
  otherwise a new UUID. Always returned in the `x-request-id` response header.
- **Per request**: one `request completed` line with `method`, `route` (template, e.g.
  `/v1/incidents/:id`; `null` for unknown routes), `status_code` and `duration_ms`. Request and
  response bodies, headers and query strings are never logged. `/healthz` and `/readyz` write
  this line at debug only (API-100-07).
- **Redaction** (`scrubber.ts`, used by the logs and by Sentry): authorization, cookies, tokens,
  passwords, secrets, OTP codes, `share_payload`, medical/emergency fields, names and invite links
  are `[REDACTED]`; emails are masked (`a***@***.test`), phones masked (`***01`); coordinates are
  omitted. Free text is scanned for bearer tokens, JWTs, invite tokens, emails and `+` phones.
- **Tracing**: OpenTelemetry (HTTP, Fastify, Postgres, ioredis) exported over OTLP/HTTP to
  `OTEL_EXPORTER_OTLP_ENDPOINT` (`/v1/traces`). Unset = no SDK is loaded or started. Span URLs
  have no query string and are scrubbed. BullMQ is traced via `bullmq-otel` once queues exist.
- **Sentry**: unexpected errors only, scrubbed, no request/user data. Unset `SENTRY_DSN` = Sentry is
  not loaded. Release = git commit: `GIT_COMMIT` env, else `dist/build-info.json` written by
  `npm run build` (from `GIT_COMMIT` or `git rev-parse HEAD`; `null` if neither). Docker:
  `docker build --build-arg GIT_COMMIT=$(git rev-parse HEAD) .`
- Both start in `observability/boot-observability.ts`, imported by `main.ts` right after the config
  and before Nest, so instrumentation is in place before Fastify, pg and ioredis load.

## CI (`.github/workflows/ci.yml`)

GitHub Actions runs on every push and pull request (all branches); any failing step fails the run.
A newer push to the same branch cancels the older run. No real credentials and no GitHub secrets:
the jobs read the repository only, and the database is a throwaway container.

| Job        | Steps                                                                                                                                                                                                                                                      |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checks`   | `npm ci`, `lint`, `format:check`, `typecheck`, `test`, `db:baseline:verify`, OpenAPI diff (`openapi:check`).                                                                                                                                               |
| `database` | `docker compose up -d --wait` (same image + shim as local, compose project `atlas-api-ci`), then `db:baseline`, `db:test:sql`, `db:migrate`, `db:seed`, and `test:baseline`, `test:int`, `test:parity` (their own containers). Runs after `checks` passes. |
| `dart`     | Regenerates `clients/dart`, fails on any difference, then `client:dart:build`. Runs after `checks` passes.                                                                                                                                                 |
| `docker`   | `docker build` of the `Dockerfile` (build only, nothing pushed). Runs after `checks` passes.                                                                                                                                                               |
| `secrets`  | gitleaks (CLI, version and checksum pinned) on the commits the push or pull request adds.                                                                                                                                                                  |

CI sets `NODE_ENV=test`, `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres` and
`REDIS_URL=redis://127.0.0.1:63799` explicitly.

Run the same steps locally (Git Bash, from the repo root; run the lines in order, each stops at its
first failure):

```sh
export NODE_ENV=test DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres REDIS_URL=redis://127.0.0.1:63799
npm ci && npm run lint && npm run format:check && npm run typecheck && npm test && npm run db:baseline:verify
docker compose -p atlas-api-ci up -d --wait   # fresh database, separate from your local atlas-api stack
npm run db:baseline && npm run db:test:sql && npm run db:migrate && npm run db:seed
npm run test:baseline && npm run test:int && npm run test:parity
npm run client:dart:generate && git status --porcelain -- clients/dart openapi.json && npm run client:dart:build
docker compose -p atlas-api-ci down -v
docker build -t atlas-api:ci .
```

Stop your local `atlas-api` stack first (`docker compose down`) since both use ports 54329 and 63799.
