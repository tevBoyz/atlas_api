# Atlas API

NestJS (Fastify) backend for the Atlas mobile app. It runs on the existing Atlas PostgreSQL 17.11
database (hosted on Supabase) and replaces the Supabase SQL functions area by area.

## Quick start (local, fake data)

Needs Node 24 (`.nvmrc`) and Docker Desktop. From a fresh clone:

```sh
npm ci
docker compose up -d --wait   # Postgres 17.11 (Supabase image) on 127.0.0.1:54329, Redis 7 on 127.0.0.1:63799
npm run db:setup              # baseline (37 migrations) + API migrations + fake seed data
npm run start:dev             # API on http://localhost:3000 (GET /healthz)
```

`db:*` scripts use the local docker database automatically when `DATABASE_URL` is not set. To
point the API itself at it, copy `.env.example` to `.env` and set the local values shown there
(`DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres`,
`REDIS_URL=redis://127.0.0.1:63799`).

## Database scripts

| Script                         | What it does                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------- |
| `npm run db:setup`             | `db:baseline`, then `db:migrate`, then `db:seed`.                                                 |
| `npm run db:baseline`          | Verifies checksums, then applies `db/baseline/*.sql` in file-name order to an **empty** database. |
| `npm run db:baseline:verify`   | Checksums only (no database).                                                                     |
| `npm run db:baseline:manifest` | Rewrites `db/baseline/checksums.sha256`. Only for a deliberate, reviewed baseline refresh.        |
| `npm run db:test:sql`          | Runs the 7 behavioural SQL tests in `db/baseline/tests/` against the local database.              |
| `npm run db:migrate`           | Applies API-owned SQL migrations from `db/migrations/` (tracked in `api_schema_migrations`).      |
| `npm run db:seed`              | Inserts fake users, complete profiles and one Safety Circle. Idempotent.                          |
| `npm run db:introspect`        | Regenerates `src/db/schema.ts` (Drizzle) from the local baselined database.                       |

### Production safety

- Every script that connects refuses any host other than `localhost`, `127.0.0.1` or `::1`, and
  refuses URLs whose query parameters (`host`, `hostaddr`, `port`, `service`) could redirect the
  connection. Output names the target as `host:port/database` only, never credentials.
- `DATABASE_URL` is resolved like the API does: a real environment variable wins over `.env`; if
  neither sets it, the local docker database is used. If your `.env` points at a hosted database,
  the scripts refuse; override it for one command instead:
  - Git Bash: `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres npm run db:seed`
  - PowerShell: `$env:DATABASE_URL='postgresql://postgres:postgres@127.0.0.1:54329/postgres'; npm run db:seed`
- `--allow-remote` (e.g. `npm run db:migrate -- --allow-remote`) lifts the rule. It exists only for
  an approved deploy step on Dawit's instruction. Never use it for tests or experiments.

### Baseline (`db/baseline/`)

The 37 Supabase migrations and 7 SQL test files are stored **unchanged** (epic §18 D1).
`db/baseline/checksums.sha256` lists a SHA-256 per file (line endings normalized, so a Windows
CRLF checkout matches). An edited, missing or unlisted file stops `db:baseline` before anything
runs. The whole baseline runs in one transaction, as the `postgres` role (as on Supabase).

Re-running is safe: when the same baseline is already applied it does nothing; any other non-empty
database is refused. The applied baseline is recorded in the local-only schema `atlas_local`.
To start over: `docker compose down -v` then `docker compose up -d --wait`.

**Local shim.** The `supabase/postgres` image has the Supabase roles, the `supabase_realtime`
publication and the initial `auth` schema, but on a real project the Auth (GoTrue) and Storage
services add the rest at startup. `db/local/supabase-services-shim.sql` adds the subset the baseline
needs (`auth.users` phone/confirmation columns, current `auth.uid()`/`auth.jwt()`, `storage.buckets`,
`storage.objects`, `storage.foldername()`). Docker runs it once, when the volume is created. It is
never applied to a hosted database.

### API migrations (`db/migrations/`)

Plain SQL, named `<number>_<snake_case>.sql`, applied in number order, each in its own transaction,
recorded in `public.api_schema_migrations (id text primary key, applied_at timestamptz)`.
**Additive and backward compatible only** while the app and the SQL functions share the database.
See `db/migrations/README.md`.

### Drizzle schema (`src/db/schema.ts`)

Generated by `npm run db:introspect` (drizzle-kit pull + a deterministic post-processing step) for
`profiles`, `safety_circles`, `safety_circle_members`, `incidents`, `incident_deliveries`,
`incident_events`, `app_config`, `login_lockouts`, plus a read-only `authUsers` subset of
`auth.users` (`id`, `email`, `phone`, `email_confirmed_at`, `phone_confirmed_at`, `created_at`).
Do not edit it by hand, and never use drizzle-kit generate/push: schema changes are SQL migrations.
Never write `activated_at` on `safety_circle_members`; the trigger owns it.

### Seed data

Fake only: Ada (circle owner), Ben and Cara (active members), Dan (pending phone invite). Emails
`*@example.test`, phones `+1 201 555-0101` to `-0104` (fictional range), fixed ids
`00000000-0000-4000-8000-…`. Never put real people's data in the seed.

## Database role (epic §18 D10)

- **Production:** the API uses the **existing database role** of the Supabase project (no dedicated
  least-privilege role for now). The connection string lives only in the server's environment /
  secret store (`DATABASE_URL`), never in the app or this repo.
- **What the API needs** (and any future dedicated role must have):
  - `USAGE` on schema `auth` and `SELECT` on `auth.users` (read-only).
  - `USAGE` on schema `public`; `SELECT, INSERT, UPDATE, DELETE` on the app tables (`profiles`,
    `safety_circles`, `safety_circle_members`, `incidents`, `incident_deliveries`,
    `incident_events`, `app_config`, `login_lockouts`, `login_lockout_rpc_throttle`) and on
    API-owned tables; `EXECUTE` on the public functions it calls during the transition.
  - Must not be `anon` or `authenticated` (the `activated_at` trigger and RLS treat those as
    clients). RLS: the API enforces authorization in code, so its role reads tables with RLS
    bypassed (`postgres` has `BYPASSRLS` on Supabase) or must be granted equivalent access.
  - **No superuser at runtime.** Migrations (`db:migrate`) need `CREATE` on schema `public`; they
    run as a deploy step, not from the running API.
- **Locally:** the API and scripts connect as `postgres` (password `postgres`, local only). As on
  Supabase it is not a superuser but has `BYPASSRLS`, owns the baseline objects and can read
  `auth.users`, which matches production.

## Errors (API-100-05, `src/common/errors`)

Every non-2xx response has one body shape (spec §11.2):

```json
{
  "error": {
    "code": "submit_emergency_alert:invalid_type",
    "message": "Choose a valid emergency type.",
    "details": {}
  }
}
```

- **Parity codes** (`fn:code`, spec §7) are typed constants in `error-codes.ts`. Raise them with
  `throw new DomainError('mark_incident_safe:not_open')`; the HTTP status comes from the central
  §11.2 table in `http-status.ts`. Messages are fixed English strings (never built from input).
  `rate_limited` takes `{ retryAfterSeconds }` (sets `Retry-After`); `login_lockout:locked` takes
  `{ details: LockoutStatus }`.
- **`@Operation('fn')`** on a route names the SQL function it replaces. A raw database
  `raise exception 'circle_full'` (the capacity trigger) then becomes `<fn>:circle_full`; a raised
  `fn:code` from an SQL function maps as-is. Any other database error is a 500.
- **Validation**: `@ZodBody(schema, codes?)`, `@ZodQuery(...)`, `@ZodParam('id', schema, codes?)`.
  The first failing field gives 422 with the operation's parity code when declared
  (`{ fields: { location_source: 'attach_incident_location:invalid_source' } }`, or `fallback` for
  any failure), else `validation:invalid_request`; `details.field` names the field (dotted path).
  Declare schema fields in the SQL function's check order (first failing check wins).
- **Generic codes** (API-only): `validation:invalid_request` 422, `internal:error` 500, and
  framework errors `http:not_found` 404 (unknown route; Fastify answers 404, not 405, for a wrong
  method), `http:bad_request` 400 (unreadable/empty JSON), `http:payload_too_large` 413,
  `http:unsupported_media_type` 415, `http:unauthorized` 401, `http:forbidden` 403, and the other
  `http:*` codes in `error-codes.ts` (any other 4xx keeps its status as `http:client_error`).
- **Unexpected errors** (and any deliberate 5xx `HttpException`) → 500 `internal:error`: no
  message, stack or SQL in the body; logged at `error` with the request id and reported to Sentry.

## Observability (API-100-06, `src/observability`)

- **Logs**: pino JSON on stdout, level from `LOG_LEVEL` (`silent` turns them off). Nest's own
  logs use the same logger. Every line of a request has `request_id`.
- **Request id**: the incoming `x-request-id` when it is 1-128 characters of `A-Z a-z 0-9 . _ : -`,
  otherwise a new UUID. Always returned in the `x-request-id` response header.
- **Per request**: one `request completed` line with `method`, `route` (template, e.g.
  `/v1/incidents/:id`; `null` for unknown routes), `status_code` and `duration_ms`. Request and
  response bodies, headers and query strings are never logged.
- **Redaction** (`scrubber.ts`, used by the logs and by Sentry): authorization, cookies, tokens,
  passwords, secrets, OTP codes, `share_payload`, medical/emergency fields, names and invite links
  are `[REDACTED]`; emails are masked (`a***@***.test`), phones masked (`***01`); coordinates are
  omitted. Free text is scanned for bearer tokens, JWTs, invite tokens, emails and `+` phones.
- **Tracing**: OpenTelemetry (HTTP, Fastify, Postgres, ioredis) exported over OTLP/HTTP to
  `OTEL_EXPORTER_OTLP_ENDPOINT` (`/v1/traces`). Unset = no SDK is loaded or started. Span URLs
  have no query string and are scrubbed. BullMQ is traced via `bullmq-otel` once queues exist.
- **Sentry**: unexpected errors only, scrubbed, no request/user data. Unset `SENTRY_DSN` = Sentry is
  not loaded. Release = git commit: `GIT_COMMIT` env, else `dist/build-info.json` written by
  `npm run build` (from `GIT_COMMIT` or `git rev-parse HEAD`; `null` if neither). Docker:
  `docker build --build-arg GIT_COMMIT=$(git rev-parse HEAD) .`
- Both start in `observability/boot-observability.ts`, imported by `main.ts` right after the config
  and before Nest, so instrumentation is in place before Fastify, pg and ioredis load.

## CI (`.github/workflows/ci.yml`)

GitHub Actions runs on every push and pull request (all branches); any failing step fails the run.
A newer push to the same branch cancels the older run. No real credentials and no GitHub secrets:
the jobs read the repository only, and the database is a throwaway container.

| Job        | Steps                                                                                                                                                                                                          |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checks`   | `npm ci`, `lint`, `format:check`, `typecheck`, `test`, `db:baseline:verify`, OpenAPI diff (`openapi:check`).                                                                                                   |
| `database` | `docker compose up -d --wait` (same image + shim as local, compose project `atlas-api-ci`), then `db:baseline`, `db:test:sql`, `db:migrate`, `db:seed`, `test:int`, `test:parity`. Runs after `checks` passes. |
| `docker`   | `docker build` of the `Dockerfile` (build only, nothing pushed). Runs after `checks` passes.                                                                                                                   |
| `secrets`  | gitleaks (CLI, version and checksum pinned) on the commits the push or pull request adds.                                                                                                                      |

CI sets `NODE_ENV=test`, `DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres` and
`REDIS_URL=redis://127.0.0.1:63799` explicitly.

Not built yet (the CI steps already exist):

- **OpenAPI diff**: runs `npm run openapi:check` once that script exists (API-100-12 adds it: it
  regenerates `openapi.json` and fails on any difference from the committed file). Until then the
  step logs "OpenAPI diff skipped" and passes.
- **Integration and parity tests**: `test/int/` and `test/parity/` are empty until the Testcontainers
  harness (API-100-13); both scripts pass with no tests.

Run the same steps locally (Git Bash, from the repo root; run the lines in order, each stops at its
first failure):

```sh
export NODE_ENV=test DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres REDIS_URL=redis://127.0.0.1:63799
npm ci && npm run lint && npm run format:check && npm run typecheck && npm test && npm run db:baseline:verify
docker compose -p atlas-api-ci up -d --wait   # fresh database, separate from your local atlas-api stack
npm run db:baseline && npm run db:test:sql && npm run db:migrate && npm run db:seed && npm run test:int && npm run test:parity
docker compose -p atlas-api-ci down -v
docker build -t atlas-api:ci .
```

Stop your local `atlas-api` stack first (`docker compose down`) since both use ports 54329 and 63799.
